PMSS Refactor Assist — Strict Rails + Compression-First Mode

Context:
PMSS is a Debian overlay OS for seedbox management. Scripts are operational contracts.
Refactoring here means: improve internals WITHOUT changing externally observable behaviour.

Goal:
Apply small, behaviour-preserving refactors that simplify PMSS while keeping all safety + updater rails intact.

Primary objective (hard):
- Reduce runtime footprint AND reduce cognitive load.
- “Reduce cognitive load” must NOT be paid for with more concepts/indirection.

Secondary objective (soft):
- Improve readability ONLY when it also reduces runtime footprint or deletes concepts.

Definition (what “refactoring” means here):
- Change internal structure without changing externally observable behaviour.
- “Externally observable” includes: CLI flags/semantics, env var names, exit codes, log/JSON field names and formats,
  file paths, operational ordering, and updater topology.

Updater topology is sacred:
install.sh → scripts/update.php (bootstrap) → scripts/util/update-step2.php (orchestration)

----------------------------------------------------------------------
RUN MODES (PICK ONE)
----------------------------------------------------------------------

Run types (pick one):

1) Compression Run (default):
   - Hard: runtime LOC and concept count must not increase.
   - Small scope (1–3 targets).

2) Safety Expansion Run (operator-approved):
   - Allowed to add runtime LOC when it materially improves safety rails/testability.
   - Still no behavior changes.

3) Architectural Simplification Run (operator-approved):
   - Goal: reduce concepts/branching across a subsystem by restructuring internals (still behavior-preserving).
   - Budget increase: up to 20 files and 2000 changed lines.
   - Must end net-negative in:
     - concepts (files + exported symbols + require hops), AND
     - runtime LOC OR complexity (measured by your snapshot tooling).
   - Must include a behavior lock:
     - either characterization tests or snapshot tests around the affected boundary.
   - No “parallel implementations” left in-tree at end (no permanent old+new).

----------------------------------------------------------------------
COMPRESSION RUN — HARD GATES (MUST HOLD)
----------------------------------------------------------------------

GATE 1: Runtime footprint must NOT increase.
- “Runtime” = scripts/* EXCLUDING:
  - scripts/lib/tests/*
  - tests/*
  - scripts/testing/*
  - docs/*, development/*, .github/*
If runtime LOC increases: STOP. Do not continue refactoring in this run.

GATE 2: Concept count must NOT increase.
“Concepts” are expensive. A concept is any of:
- a new runtime file
- a new require/include hop in runtime paths
- a new global function
- a new global class
- a new public entrypoint (scripts/*, scripts/util/*, scripts/cron/*, scripts/cli/*)

If you add a concept, you must delete >= 1 concept in the same run.
Prefer net concept deletion.

GATE 3: No micro-helpers.
Avoid creating helpers/modules/classes for tiny duplication.
Local duplication is allowed when:
- duplicated block ≤ 4 lines AND occurs in ≤ 4 places
AND the block does NOT represent a safety-critical invariant.

Safety-critical invariant examples:
- anything touching /home paths, deletes, chmod/chown, user identities, apt/dpkg sequencing,
  shell command composition, or updater phase boundaries.
If the duplication is safety-critical, prefer ONE authoritative implementation even if small.

GATE 4: Prefer inlining over indirection.
If you find trivial wrappers / helpers (delegate-only), inline them and delete the wrapper.
(Trivial wrapper = calls another function/method with no logic.)

----------------------------------------------------------------------
HELPER / EXTRACTION ROI (MECHANICAL GATE)
----------------------------------------------------------------------

Before extracting ANY helper (function/class/file), compute an estimate:

Let:
- N = number of call sites that would use the helper
- M = duplicated lines per site that would be removed
- C = call overhead lines per site (usually 1; sometimes 2)
- H = helper body lines + required docblock lines + include/require lines + guards/shim overhead

Approx net delta:
  delta = H + (N * C) - (N * M)

Rules:
- If delta >= -5 (does NOT save at least ~5 runtime lines), DO NOT extract.
- If extraction would add a new concept (new runtime file, new require hop, new global symbol),
  require delta <= -15 OR delete at least one existing concept in the same run.
- Prefer deleting existing helpers used in <= 4 call sites and <= ~10 LOC body by inlining.

Notes:
- DRY is not an absolute. Over-abstraction is a refactoring failure mode.
- If you must centralize for safety invariants, prefer doing it INSIDE an existing subsystem module/class,
  not a new global helpers file.

----------------------------------------------------------------------
STYLE / STRUCTURE PREFERENCES (BEAUTY LEVER)
----------------------------------------------------------------------

When two behaviour-equivalent options exist, choose the one with:
- fewer concepts (fewer files, fewer global symbols, fewer require hops),
- fewer branches and less nesting,
- fewer total runtime lines.

Abstraction ladder (use the lowest rung that works):
1) DELETE code / dead paths / redundant wrappers.
2) FLATTEN nesting with guard clauses / early returns (must not change side effects/order).
3) Use a LOCAL table/map (inside the same file/function) instead of long if/elseif ladders when it compresses.
4) Use a LOCAL helper in the same file (private method / file-scoped function) ONLY if it passes ROI.
5) Use an EXISTING subsystem class/module (add a method there) if it avoids new concepts and passes ROI.
6) Create a NEW module/file/class ONLY if it deletes more code/concepts than it adds (hard gate).

PHP structure preference:
- Prefer cohesive classes with methods over adding more global helper functions.
- Avoid new “helpers.php” dumping grounds.
- Avoid function_exists/class_exists guard patterns unless you are forced by legacy include topology.

File length:
- ~150 LOC is a guideline, not a target. NEVER split files solely to hit a line count.
- Splitting is allowed ONLY when it reduces concepts OR deletes runtime LOC.

Comments/docblocks:
- Comments are for WHY, hazards, invariants, and contracts.
- Do NOT add filler comments to satisfy ratios.
- Prefer removing redundant comments and making code self-explanatory.
- Docblock lint must not regress, but do not introduce new exported symbols that require docblocks unless you are deleting more.

----------------------------------------------------------------------
HARD RAILS (ALWAYS)
----------------------------------------------------------------------

- PHP 7.3 only.
- Do not add external deps/tools/configs unless operator approves.
- No behaviour changes: flags/env/exit/log/json/paths/order/topology.
- No safety regressions; never weaken destructive guards.
- Never modify:
  - etc/skel/www (locked)
  - third-party/vendor trees
  - dpkg baseline files under scripts/lib/update/dpkg/selections*.txt
- Do not change updater topology or dpkg/apt phase ordering.

Concurrency & Shared Worktree (NEW — HARD)

- Assume multiple Codex sessions/agents may run in the same git worktree concurrently.
- Treat pre-existing modified/untracked files as owned by another run unless the operator explicitly assigns them to you.
- Ignore unrelated changes: do not “clean up” or “fix” other files just because they are modified.
- Never run `git clean`, `git reset --hard`, `git restore`, or any destructive git command unless explicitly ordered by the operator.
- Only touch files required for your task; treat already-modified files as off-limits unless the operator explicitly assigns them to you for this run (or use a separate worktree).
- Stage changes with explicit paths only (`git add <file>`); never use `git add .` or broad globs.

----------------------------------------------------------------------
WORKFLOW (DO THIS)
----------------------------------------------------------------------

1) Read first:
   - AGENTS.md, AGENTS.local.md, any nested AGENTS.md in scope
   - docs/architecture.md, docs/update.md, docs/refactoring.md
   - relevant docs/adr/* and docs/incidents/* for the subsystem

2) Pick targets (compression run):
   - Pick 1–3 targets max.
   - Prefer the highest-value, highest-duplication / highest-nesting hot spots.
   - Avoid roaming.

3) Non-goals gate:
   - Explicitly state you are NOT doing feature work, rewrites, interface changes, or style cleanups.

4) For each chosen refactor (before editing), state:
   - Purpose: cost-of-change / risk reduction / leverage / provability
   - Metrics: runtime LOC delta target, duplicated blocks removed, max nesting reduced, concepts deleted
   - Invariants: 3–7 bullets (outputs/paths/order/log markers stable)

5) Implement minimal edits:
   - Keep behaviour identical.
   - Prefer deletion + inlining + flattening before extraction.
   - If a change would violate compression gates, drop it.

6) Verification:
   - php -l on changed PHP files
   - php scripts/lib/tests/development/Runner.php when touching scripts/lib helpers or PHP entrypoints
   - scripts/testing/php-lint-compat.sh
   - scripts/testing/test-php.sh
   - scripts/testing/test-bash.sh
   - scripts/testing/php73-compat-scan.sh
   - scripts/testing/docblock-lint.sh when applicable

7) Summarise (review-first):
   - List every changed file and why
   - What you deleted/simplified and why it reduces concepts/runtime LOC
   - Why it is behaviour-preserving (which invariants you relied on)
   - Scorecard:
     - runtime LOC delta (added/removed, by path)
     - concepts added/deleted
     - helpers removed/added
     - max nesting delta (best-effort)
   - Commands run

No commits unless the operator explicitly instructs you to.
No new branches unless explicitly instructed.

Change budget:
- Compression/Safety runs: ≤ 8 files touched, ≤ 800 total changed lines (additions + deletions)
- Architectural Simplification runs: ≤ 20 files touched, ≤ 2000 total changed lines (additions + deletions)
Stop if budget is reached.
