PMSS Refactor Assist — Strict Rails + Balanced Refactor Mode

Context:
PMSS is a Debian overlay OS for seedbox management. Scripts are operational contracts.
Refactoring here means: improve internals WITHOUT changing externally observable behaviour.

Goal:
Apply small, behaviour-preserving refactors that simplify PMSS while keeping all safety + updater rails intact.

Primary objective (hard):
- Reduce runtime footprint AND reduce cognitive load.
- “Reduce cognitive load” must NOT be paid for with more concepts/indirection.
- Compression credit must come from deleting or simplifying executable code paths; comment-only/whitespace-only reductions do not count.

Secondary objective (soft):
- Improve readability ONLY when it also reduces runtime footprint or deletes concepts.

Definition (what “refactoring” means here):
- Change internal structure without changing externally observable behaviour.
- “Externally observable” includes: CLI flags/semantics, env var names, exit codes, log/JSON field names and formats,
  file paths, operational ordering, and updater topology.

Updater topology is sacred:
install.sh → scripts/update.php (bootstrap) → scripts/util/update-step2.php (orchestration)

----------------------------------------------------------------------
RUN MODES (PICK ONE)
----------------------------------------------------------------------

Run types (pick one):

1) Balanced Refactor & Compression Run (default):
   - Goal: Mix of structural improvement and dead code removal.
   - Scope: Moderate (5–15 targets).
   - "Bigger stuff": Allowed to tackle slightly larger subsystems than simple peephole optimization.
   - Test-First: Strongly consider writing a targeted test case (scripts/lib/tests/development) BEFORE changing logic to ensure safety.
   - Constraint: Aim for net-negative or neutral LOC/concepts, but clarity/safety improvements are allowed to cost small LOC.

2) Safety Expansion Run (operator-approved):
   - Allowed to add runtime LOC when it materially improves safety rails/testability.
   - Still no behavior changes.

3) Architectural Simplification Run (operator-approved):
   - Goal: reduce concepts/branching across a subsystem by restructuring internals (still behavior-preserving).
   - Budget increase: up to 20 files and 2000 changed lines.
   - Must end net-negative in:
     - concepts (files + exported symbols + require hops), AND
     - runtime LOC OR complexity (measured by your snapshot tooling).
   - Must include a behavior lock:
     - either characterization tests or snapshot tests around the affected boundary.
   - No “parallel implementations” left in-tree at end (no permanent old+new).

----------------------------------------------------------------------
Compression & Indirection Rails (NEW — HARD)
----------------------------------------------------------------------

Comment & Docblock Integrity (NEW — HARD)

- Comments/docblocks are NOT a compression lever.
- Do not change, delete, collapse, or rewrap comments/docblocks just to hit LOC targets.
- Comment/docblock edits are allowed ONLY when:
  (a) the surrounding code changed and the comment must be updated to stay correct, OR
  (b) the comment is factually wrong / misleading / unsafe, OR
  (c) the comment became truly redundant because the surrounding code was refactored to be self-explanatory (not for LOC credit).
- Never remove contract detail from exported/public symbols:
  - keep @param/@return/@throws tags when present; do not collapse multi-line PHPDoc that contains tags.
- No comment-only churn:
  - If a diff hunk touches only comments/whitespace (no code), revert it unless it satisfies (a), (b), or (c) above.
- Style:
  - Use // for single-line comments.
  - Use /* ... */ for non-PHPDoc block comments.
  - Use /** ... */ only for real PHPDoc blocks (functions/files that need doc tooling).

----------------------------------------------------------------------
BALANCED / COMPRESSION GATES
----------------------------------------------------------------------

GATE 1: Runtime footprint should decrease or remain neutral.
- “Runtime” = scripts/* EXCLUDING:
  - scripts/lib/tests/*
  - tests/*
  - scripts/testing/*
  - docs/*, development/*, .github/*
If runtime LOC increases significantly without safety justification: STOP. Do not continue refactoring in this run.

GATE 2: Concept count should NOT increase.
“Concepts” are expensive. A concept is any of:
- a new runtime file
- a new require/include hop in runtime paths
- a new global function
- a new global class
- a new public entrypoint (scripts/*, scripts/util/*, scripts/cron/*, scripts/cli/*)

If you add a concept, aim to delete >= 1 concept in the same run.
Prefer net concept deletion.

GATE 3: No micro-helpers.
Avoid creating helpers/modules/classes for tiny duplication.
Local duplication is allowed when:
- duplicated block ≤ 4 lines AND occurs in ≤ 4 places
AND the block does NOT represent a safety-critical invariant.

Safety-critical invariant examples:
- anything touching /home paths, deletes, chmod/chown, user identities, apt/dpkg sequencing,
  shell command composition, or updater phase boundaries.
If the duplication is safety-critical, prefer ONE authoritative implementation even if small.

GATE 4: Prefer inlining over indirection.
If you find trivial wrappers / helpers (delegate-only), inline them and delete the wrapper.
(Trivial wrapper = calls another function/method with no logic.)

----------------------------------------------------------------------
HELPER / EXTRACTION ROI (MECHANICAL GATE)
----------------------------------------------------------------------

Before extracting ANY helper (function/class/file), compute an estimate:

Let:
- N = number of call sites that would use the helper
- M = duplicated lines per site that would be removed
- C = call overhead lines per site (usually 1; sometimes 2)
- H = helper body lines + required docblock lines + include/require lines + guards/shim overhead

Approx net delta:
  delta = H + (N * C) - (N * M)

Rules:
- If delta >= -5 (does NOT save at least ~5 runtime lines), DO NOT extract.
- If extraction would add a new concept (new runtime file, new require hop, new global symbol),
  require delta <= -15 OR delete at least one existing concept in the same run.
- Prefer deleting existing helpers used in <= 4 call sites and <= ~10 LOC body by inlining.

Notes:
- DRY is not an absolute. Over-abstraction is a refactoring failure mode.
- If you must centralize for safety invariants, prefer doing it INSIDE an existing subsystem module/class,
  not a new global helpers file.

----------------------------------------------------------------------
STYLE / STRUCTURE PREFERENCES (BEAUTY LEVER)
----------------------------------------------------------------------

When two behaviour-equivalent options exist, choose the one with:
- fewer concepts (fewer files, fewer global symbols, fewer require hops),
- fewer branches and less nesting,
- fewer total runtime lines.

Abstraction ladder (use the lowest rung that works):
1) DELETE code / dead paths / redundant wrappers.
2) FLATTEN nesting with guard clauses / early returns (must not change side effects/order).
3) Use a LOCAL table/map (inside the same file/function) instead of long if/elseif ladders when it compresses.
4) Use a LOCAL helper in the same file (private method / file-scoped function) ONLY if it passes ROI.
5) Use an EXISTING subsystem class/module (add a method there) if it avoids new concepts and passes ROI.
6) Create a NEW module/file/class ONLY if it deletes more code/concepts than it adds (hard gate).

PHP structure preference:
- Prefer cohesive classes with methods over adding more global helper functions.
- Avoid new “helpers.php” dumping grounds.
- Avoid function_exists/class_exists guard patterns unless you are forced by legacy include topology.

File length:
- ~150 LOC is a guideline, not a target. NEVER split files solely to hit a line count.
- Splitting is allowed ONLY when it reduces concepts OR deletes runtime LOC.

Comments:
- Comments exist to preserve invariants, hazards, and WHY.
- Do not add filler comments for ratios.
- Do not delete or compress comments to achieve LOC goals; only remove comments if they are truly redundant AFTER code was made self-explanatory.

HARD RAILS (ALWAYS)
----------------------------------------------------------------------

- PHP 7.3 only.
- Do not add external deps/tools/configs unless operator approves.
- No behaviour changes: flags/env/exit/log/json/paths/order/topology.
- No safety regressions; never weaken destructive guards.
- Validation and constraint strictness are observable behaviors. Changing a minimum
  threshold, widening an allowed range, removing a validation check, or altering a
  guard condition is a BEHAVIOR CHANGE, not a refactor. These are out of scope for
  any refactor run regardless of whether tests still pass.
- Repository policy freeze:
  - Do not change MediaArea repository handling now that it works.
  - Do not implement a general deb822 migration for Debian apt sources without explicit operator instruction/ADR (see `docs/adr/0008-reject-deb822-apt-sources-migration.md`; Docker deb822 is already in use; keep as-is).
- Never modify:
  - vendor/third-party trees (ruTorrent upstream, _lib/, etc.) — first-party skel files are editable
  - third-party/vendor trees
  - dpkg baseline files under scripts/lib/update/dpkg/selections*.txt
- Do not change updater topology or dpkg/apt phase ordering.

----------------------------------------------------------------------
FILE / FUNCTION DELETION PROTOCOL (HARD GATE)
----------------------------------------------------------------------

Before deleting ANY file or function, you MUST complete ALL of these checks:

REFERENCE AUDIT (mandatory):
1. grep -r for the function name across ALL of scripts/, install.sh, and development/
2. grep -r for the filename (basename) in case it's loaded via include/require string
3. Check if the file is loaded via glob patterns (e.g., foreach glob('apps/*.php'))
4. Check shell scripts: install.sh, scripts/update.php, scripts/util/update-step2.php, scripts/cron/*, scripts/cli/*
5. Check systemd units and crontab templates under etc/
6. Check docs for the symbol (start with docs/contracts.md, then docs/) and update/remove stale contract references
7. Check tests (scripts/lib/tests/, tests/) for symbol references and update/remove as needed

CONTEXT AUDIT (mandatory):
1. Read the file's docblock header - look for:
   - Invocation contexts (install.sh, cron, CLI, update-step2)
   - External callers documented
   - @since tags indicating long-standing infrastructure
   - @see links to documentation/changelogs
2. A comment about a DEPRECATED FEATURE INSIDE a file does NOT mean the file itself is dead
   - Example: "Compatibility fix for systems where quota was compiled from source" is about a SHIM inside the file, not the file's purpose
3. Check if the function/file is infrastructure vs feature code:
   - Infrastructure (quotas, permissions, network, certificates) often has external callers not visible in PHP
   - Feature code (apps, services) is more likely to be self-contained

DELETION ALLOWED only when ALL of these are true:
- ZERO runtime references found in PHP code (grep audit)
- NOT called from shell scripts (install.sh, update.php, cron/*, cli/*)
- NOT loaded by glob patterns or dynamic includes
- Docblock does NOT document external callers
- NOT infrastructure code with potential shell/cron callers
- File/function is clearly orphaned (e.g., explicitly skipped in loading loop, or feature was removed)

DELETION BLOCKED when ANY of these are true:
- Any runtime reference exists
- Docblock mentions install.sh, cron, CLI, or external invocation
- File is under scripts/util/ (often called from shell scripts)
- File handles: quotas, permissions, certificates, network config, apt/dpkg
- Uncertain about external callers — ask operator

When in doubt: DO NOT DELETE. Mark as potential dead code in your summary and let operator decide.

Parallel Runs (ABSURDLY SIMPLE)

- You MAY run multiple Codex runs in the same checkout.
- Each run MUST declare a SCOPE (subtree/glob) and touch only that scope.
- Rule: never edit a file that is already dirty (within your SCOPE).
  - Before touching a file: if it appears in `git status --porcelain` AND is inside the SCOPE, SKIP it.
- Dirty files outside the SCOPE do not block the run; ignore them and do not touch them.
- If “dirty files at start” includes anything in the SCOPE: do NOT halt the run; keep working, but avoid editing those dirty files. Pick different targets within the SCOPE, or ask the operator if you must touch them.
- Never `git add .` or `git commit -a`. Stage only files you changed.
- Autocommit only if the only dirty files within the SCOPE are the files you touched (per `git status --porcelain`); dirty files outside the SCOPE do not block, and must remain untouched.

----------------------------------------------------------------------
WORKFLOW (DO THIS)
----------------------------------------------------------------------

1) Startup reads (before proceeding):
   - AGENTS.md (rails / Constitution / doctrine; treat as binding).
   - AGENTS.local.md (host-specific local rails, if exists).

2) Task-relevant reads (based on refactor scope):
   - Any nested AGENTS.md covering files you touch (most-specific instructions win).
   - Relevant docs under docs/ (architecture, update, refactoring, etc.).
   - Relevant ADRs under docs/adr/ and incidents under docs/incidents/ for the subsystem.

3) Pick targets (balanced run):
   - Pick 5–15 targets max.
   - Prefer the highest-value, highest-duplication / highest-nesting hot spots.
   - Avoid roaming.

4) Non-goals gate:
   - Explicitly state you are NOT doing feature work, rewrites, interface changes, or style cleanups.

5) For each chosen refactor (before editing), state:
   - Purpose: cost-of-change / risk reduction / leverage / provability
   - Metrics: runtime LOC delta target, duplicated blocks removed, max nesting reduced, concepts deleted
   - Invariants: 3–7 bullets (outputs/paths/order/log markers stable)

6) Implement (Test-Driven where applicable):
   - If the logic is complex or risky, create a test case FIRST (scripts/lib/tests/development) to pin down current behavior.
   - Implement minimal edits.
   - Keep behaviour identical.
   - Prefer deletion + inlining + flattening before extraction.
   - If a change would violate gates (without justification), drop it.

7) Verification:
   - php -l on changed PHP files
   - php scripts/lib/tests/development/Runner.php when touching scripts/lib helpers or PHP entrypoints
   - scripts/testing/php-lint-compat.sh
   - scripts/testing/test-php.sh
   - scripts/testing/test-bash.sh
   - scripts/testing/php73-compat-scan.sh
   - scripts/testing/docblock-lint.sh when applicable

8) Summarise (review-first):
   - List every changed file and why
   - Dirty files at start (`git status --porcelain`)
   - Dirty files at end (`git status --porcelain`)
   - What you deleted/simplified and why it reduces concepts/runtime LOC
   - Why it is behaviour-preserving (which invariants you relied on)
   - Scorecard:
     - runtime LOC delta (added/removed, by path)
     - concepts added/deleted
     - helpers removed/added
     - max nesting delta (best-effort)
   - Commands run

No commits unless the operator explicitly instructs you to.
Autocommit: When Autocommit Mode is appended below, "no commits" is VOID.
No new branches unless explicitly instructed.

Change budget:
- Balanced/Safety runs: ≤ 20 files touched, ≤ 2000 total changed lines (additions + deletions)
- Architectural Simplification runs: ≤ 30 files touched, ≤ 3000 total changed lines (additions + deletions)
Stop if budget is reached.

Autocommit budget (when Autocommit Mode is active):
- Balanced: 25 targets, 40 files, 5000 lines (gates GATE 1-4 still apply at full strength)
- Architectural: 50 files, 6000 lines (gates still apply)
- Work in batches: 5-10 related changes → verify → commit → continue.
