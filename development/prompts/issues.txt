Absolutes:
- NEVER CREATE GIT BRANCHES.
- Do not commit or push unless the operator explicitly instructs you to.
- ABSOLUTELY NO ZFS.
- NEVER remove, weaken, loosen, or make unreachable any validation check, minimum,
  maximum, constraint, or security guard to resolve a mismatch with an upstream or
  external component. When upstream input fails PMSS validation, fix the upstream
  component. Absence of a test for the constraint does NOT mean it is unintentional;
  assume all constraints are intentional unless git history says otherwise.
- NEVER make validation unreachable by removing its call, adding an early return before
  it, deprecating the function without a replacement, or wrapping it in dead code.
  This is equivalent to removing the validation.
- Before removing or relaxing any constraint, run:
    git log -n 10 --format="%h %ae %s" --follow -- <file>
  If any author is NOT a bot (non-noreply@ email): the constraint was added by a human
  contributor. Do NOT add a human-delegation label; follow the BLOCKED ISSUE FEEDBACK
  flow below and skip the implementation. Do not implement the removal.
- Keep diffs small, idempotent, backward-compatible; reuse existing helpers.

Autocommit: When Autocommit Mode is appended below, "do not commit or push" is VOID.

Workflow (Do This Now):
- Fix direction: when an issue contains a ## Suggested Fix section, that section is the
  primary hypothesis for the implementation direction — it reflects independent
  investigation, not just the title. Titles compress context and can imply the wrong
  component is the problem. If title and Suggested Fix conflict: follow the Suggested
  Fix. If Suggested Fix is absent or vague: implement the most conservative fix that
  addresses the root cause without reducing any constraint's strictness.
- Read the issue details from context files below.
- For EACH issue, assess: can this be fully resolved within this session?
  SKIP if the issue:
  - Requires external system access (SSH, package install, DC visit)
  - Touches vendor/third-party trees or dpkg selections
  - Requires multi-server coordination or production deployment
  - Is an investigation/research issue with no clear code fix
- Would take more than ~500 lines of changes (partial progress with wip: prefix is acceptable)
  - Requires making a validation check, minimum, maximum, constraint, or security guard
    less restrictive (removing it, lowering a threshold, widening allowed values, making
    an exception into a warning, or making a guard optional) — the root fix belongs in
    the component that produces the non-conforming input, not in the downstream validator
  Note why you skipped it.
- BLOCKED ISSUE FEEDBACK (important — enables autonomous cycle health):
  When you skip an issue, FIRST check its existing comments — if a previous
  cycle already posted a blocking explanation and nothing has changed (no new
  comments, no new information since the last skip comment), do NOT post again.
  Instead investigate whether the situation has changed that might unblock it.
  If it IS the first skip, or you have NEW information about what's blocking:
    gh issue comment $ISSUE_NUMBER --body "BLOCKED: <one-sentence reason>.
    Missing: <what specific info/access/change is needed to unblock>.
    Attempted: <what you tried before skipping>."
  Keep it factual and short. Do not repeat yourself across cycles.
  Then move to the next issue.
- For tractable issues: implement the smallest coherent fix/feature.
- Verify locally:
  * php -l <each changed PHP file>
  * php scripts/lib/tests/development/Runner.php
  * scripts/testing/test-php.sh
  * scripts/testing/test-bash.sh
  * scripts/testing/php73-compat-scan.sh
  * scripts/testing/php-lint-compat.sh
  * scripts/testing/docblock-lint.sh
  * scripts/testing/doctrine-lint.sh
- One commit per issue. Include "Refs #N" in the commit message.
- Partial progress IS acceptable: if the issue is too large for one session, commit what compiles and passes tests with a wip: prefix. Do NOT throw away working code because the issue is not 100% complete.
- For complex issues, multiple commits are allowed. Each must pass verification and include Refs #N.
- Commit prefix: fix: for bugs, feat: for features, security: for security issues, wip: for partial progress on complex issues.
- After commit: gh issue edit N --add-label complete-verify (best-effort).
